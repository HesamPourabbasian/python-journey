# Raising Exceptions & Exception Chaining in Python

## Introduction

In software architecture, writing defensive and self-healing systems requires more than merely catching errors generated by the Python runtime. When designing functions, classes, libraries, and public APIs, an engineer must actively enforce **Preconditions, Invariants, and Business Constraints**. If a caller passes a negative salary to a payroll calculation, supplies an empty string as an API key, or attempts to withdraw more money than an account holds, the function must refuse to proceed and explicitly signal failure.

In Python, this signaling mechanism is performed using the **`raise`** statement.

Beyond basic exception raising, professional Python engineering requires translating low-level, internal implementation errors (such as raw database driver timeouts or filesystem socket errors) into clean, high-level **Domain Exceptions**. Introduced in **PEP 3134**, Python provides **Exception Chaining (`raise ... from ...`)**, allowing developers to wrap underlying technical exceptions while preserving the complete diagnostic cause chain or cleanly suppressing internal noise using **`from None`**.

This lesson builds directly upon [Try, Except, Else & Finally](try-except-finally.md), giving you full mastery over error signaling, traceback preservation, and exception translation architectures.

## Core Concept: Error Signaling & Exception Chaining

When you raise an exception, execution in the current function halts immediately, and Python begins unwinding the call stack searching for an active handler:

```
                              EXCEPTION RAISING & CHAINING PIPELINE

   1. EXPLICIT RAISING
      if balance < amount:
          raise ValueError("Insufficient funds")  ──► Unwinds Call Stack
                                                            │
   2. RE-RAISING                                            ▼
      try: ...                                    [ Propagates to Caller ]
      except Exception:
          logger.error("Logged!")
          raise                                   ──► Preserves Original Traceback Intact!
                                                            │
   3. EXCEPTION TRANSLATION (PEP 3134)                      ▼
      try:
          raw_db_socket.connect()
      except OSError as err:
          # Explicit Chaining:
          raise DatabaseConnectionError("DB Down") from err
          # Links 'err' as the __cause__ of DatabaseConnectionError!
```

## Syntax & Essential Raising Forms

```python
# 1. Raising a Standard Exception with Diagnostic Message
def set_user_age(age: int):
    if not isinstance(age, int) or age < 0 or age > 150:
        raise ValueError(f"Invalid age: {age}. Must be an integer between 0 and 150.")

# 2. Re-raising an Active Exception (Bare raise)
try:
    process_payment()
except PaymentError as err:
    audit_logger.error(f"Payment failed: {err}")
    raise  # Re-raises the EXACT same exception with original traceback!

# 3. Explicit Exception Chaining (raise ... from exc)
try:
    val = int(raw_config_string)
except ValueError as err:
    # Wrap ValueError inside a domain-specific ConfigurationError
    raise ConfigurationError("Invalid port in configuration file.") from err

# 4. Suppressing Internal Exception Context (raise ... from None)
try:
    with open("/internal/secret/key.pem") as f:
        key = f.read()
except FileNotFoundError:
    # Hides the internal file path from the caller's traceback!
    raise SecurityKeyMissingError("Authentication service key unavailable.") from None
```

## Detailed Explanation

### 1. Re-raising: Bare `raise` vs `raise exc`

When catching an exception to log or perform cleanup before passing it up the call stack, always use a **bare `raise`**:

- **Bare `raise` (Correct)**: Preserves the **original traceback line numbers** where the error initially occurred.
- **`raise exc` (Avoid)**: Resets the traceback origin to the `except` line, destroying the original debugging context!

```python
# AVOID (Loses original traceback origin):
try:
    val = int("not_a_number")
except ValueError as err:
    logger.error("Error occurred")
    raise err  # Traceback will point to THIS line, not where int() failed!

# GOOD (Preserves exact original line numbers):
try:
    val = int("not_a_number")
except ValueError:
    logger.error("Error occurred")
    raise      # Cleanly re-raises with original stack intact! ✅
```

---

### 2. Exception Chaining Mechanics: `__cause__` vs `__context__` (PEP 3134)

In Python 3, exception objects maintain two special chaining attributes:

1. **`__context__` (Implicit Chaining)**: Automatically populated when an exception occurs *inside* an `except` block. Python prints:
   `During handling of the above exception, another exception occurred: ...`
2. **`__cause__` (Explicit Chaining)**: Populated when you use **`raise NewException from original_exc`**. Python prints:
   `The above exception was the direct cause of the following exception: ...`

```python
class PaymentGatewayError(Exception): pass

def charge_card(token: str, amount: float):
    try:
        raw_socket_call(token, amount)
    except ConnectionResetError as socket_err:
        # Explicit Chaining establishes clear causality!
        raise PaymentGatewayError(f"Failed to charge ${amount:.2f}") from socket_err
```

---

### 3. Context Suppression with `raise ... from None`

In production microservices and public SDKs, internal tracebacks often contain sensitive file paths, internal database IP addresses, or irrelevant low-level details.

By writing **`from None`**, you explicitly set `__cause__ = None` and suppress `__context__`, producing a clean, polished traceback:

```python
def query_user_record(user_id: int) -> dict:
    try:
        return internal_database_driver.execute_raw_sql(user_id)
    except RawSQLDriverError:
        # Hides the raw SQL syntax and driver tracebacks from the API consumer:
        raise UserNotFoundError(f"User #{user_id} does not exist.") from None
```

---

### 4. `assert` vs `raise`: The Critical Difference

A common mistake is using `assert condition, "error"` for input validation in production code.

**The Danger of Assertions**:
Assertions are designed strictly for **internal developer debugging**. When Python runs in optimized mode (`python -O`), the compiler **completely strips and ignores all `assert` statements**!

```python
# CRITICAL SECURITY VULNERABILITY (Bypassed with 'python -O'!):
def transfer_money(user, amount):
    assert user.is_authenticated, "Unauthorized!"  # STRIPPED in python -O!
    assert amount > 0, "Invalid amount!"           # STRIPPED in python -O!
    user.balance -= amount

# PRODUCTION-SAFE PATTERN (Never stripped):
def transfer_money(user, amount):
    if not user.is_authenticated:
        raise PermissionError("Unauthorized access attempt.")
    if amount <= 0:
        raise ValueError(f"Transfer amount must be positive, got {amount}")
    user.balance -= amount
```

## Examples

### 1. Simple: Input Precondition Validation
Enforcing constraints on mathematical domain functions.

```python
import math

def calculate_log_odds(probability: float) -> float:
    """Calculate the logit log-odds for a given probability."""
    if not isinstance(probability, (int, float)):
        raise TypeError(f"Probability must be a float, got {type(probability).__name__}")
    if not (0.0 < probability < 1.0):
        raise ValueError(f"Probability must be strictly between 0 and 1 (exclusive), got {probability}")
        
    return math.log(probability / (1.0 - probability))

print("Log-odds (0.75):", round(calculate_log_odds(0.75), 4))

# Test boundary failure:
try:
    calculate_log_odds(1.5)  # Raises ValueError
except ValueError as err:
    print("Caught Expected Validation Error:", err)
```

### 2. Beginner: Re-raising Active Exceptions After Audit Logging
Logging security events and immediately re-raising to halt execution.

```python
class SecurityAuditEvent:
    @staticmethod
    def log_unauthorized_access(user: str, resource: str):
        print(f"🚨 [SECURITY AUDIT LOG] Unauthorized access attempt by '{user}' on '{resource}'")

def access_secure_vault(user: str):
    try:
        if user != "hesam_admin":
            raise PermissionError(f"User '{user}' lacks clearance level 5.")
        print(f"Access granted to vault for: {user}")
    except PermissionError as perm_err:
        SecurityAuditEvent.log_unauthorized_access(user, "VAULT_SEC_01")
        raise  # Re-raise to ensure caller knows operation was blocked!

try:
    access_secure_vault("guest_user")
except PermissionError as err:
    print(f"Caller intercepted: {err}")
```

### 3. Intermediate: Exception Translation in a Database Layer
Wrapping low-level `sqlite3` exceptions in high-level domain repository exceptions.

```python
import sqlite3

class RepositoryError(Exception): pass
class EntityNotFoundError(RepositoryError): pass
class DatabaseConnectionError(RepositoryError): pass

class UserDataRepository:
    def __init__(self, db_path: str):
        self.db_path = db_path

    def get_user_by_id(self, user_id: int) -> dict:
        try:
            conn = sqlite3.connect(self.db_path)
            cursor = conn.cursor()
            cursor.execute("SELECT id, username FROM users WHERE id = ?", (user_id,))
            row = cursor.fetchone()
            conn.close()
        except sqlite3.OperationalError as sql_err:
            # Explicit Chaining: Translates internal SQLite error into domain error
            raise DatabaseConnectionError("Database query failed due to connection error.") from sql_err
            
        if row is None:
            raise EntityNotFoundError(f"User with ID {user_id} not found.")
            
        return {"id": row[0], "username": row[1]}

repo = UserDataRepository("non_existent_db.sqlite")

try:
    repo.get_user_by_id(101)
except RepositoryError as domain_err:
    print("Intercepted Domain Error :", domain_err)
    print("Root Technical Cause     :", domain_err.__cause__)
```

### 4. Real-World: Public SDK Clean Traceback with `from None`
Building a clean public-facing API client that conceals internal network details.

```python
class APIClientException(Exception): pass
class ResourceNotFoundException(APIClientException): pass

def fetch_remote_user_profile(user_id: str) -> dict:
    try:
        # Simulate low-level HTTP client call failing with a 404
        raise ConnectionResetError("TCP Socket Connection Reset by Peer (10.0.4.12:443)")
    except ConnectionResetError:
        # Suppress internal socket connection noise:
        raise ResourceNotFoundException(f"Profile '{user_id}' could not be located.") from None

try:
    fetch_remote_user_profile("USR-9901")
except ResourceNotFoundException as err:
    print("Clean Public API Exception:", err)
```

### 5. Advanced: Programmatic Inspection of Exception Cause Chains
Traversing the complete linked list of `__cause__` and `__context__` objects dynamically.

```python
def print_exception_chain(exc: BaseException):
    """Walk up the linked list of causal exceptions."""
    print("=" * 60)
    print("              EXCEPTION CAUSE CHAIN AUDIT")
    print("=" * 60)
    current = exc
    depth = 0
    
    while current is not None:
        chain_type = "Explicit (__cause__)" if current is exc or current == getattr(exc, '__cause__', None) else "Implicit (__context__)"
        print(f"[Level {depth}] {type(current).__name__}: {current} ({chain_type})")
        current = current.__cause__ or current.__context__
        depth += 1
        
    print("=" * 60)

# Generate a 3-layer chained exception
try:
    try:
        int("invalid_number")
    except ValueError as e1:
        raise LookupError("Lookup failed due to bad conversion") from e1
except LookupError as e2:
    try:
        raise RuntimeError("Application crashed during recovery") from e2
    except RuntimeError as e3:
        print_exception_chain(e3)
```

---

## Code Explanation

In Example 5 (Inspecting Exception Chains):
1. When `e1` (`ValueError`) occurs, `LookupError` is raised explicitly `from e1`.
2. Python sets `LookupError.__cause__ = e1`.
3. When `RuntimeError` is raised `from e2`, Python sets `RuntimeError.__cause__ = e2`.
4. `print_exception_chain` traverses the linked list of `__cause__` references, displaying the entire lineage from root cause to top-level failure.
5. This showcases how Python preserves full diagnostic provenance across architectural layers.

## Common Mistakes

### Mistake 1: Using `assert` for Production Business Logic
Assertions are disabled when running with the `-O` optimization flag (`python -O app.py`). Always use `if condition: raise ValueError(...)` for input validation.

### Mistake 2: Raising Generic `Exception` Without Context
Raising `raise Exception("error")` forces callers to catch the broad `Exception` class. Always raise specific types (`ValueError`, `TypeError`, `KeyError`, or custom domain subclasses).

---

## Best Practices

### Use `raise ... from original_exc` When Translating Errors
Whenever catching a low-level error to raise a high-level domain error, always chain the original exception using `from original_exc`.

Good:
```python
try:
    config = json.loads(raw_text)
except json.JSONDecodeError as err:
    raise ConfigurationError("Malformed JSON configuration file.") from err
```

Avoid:
```python
try:
    config = json.loads(raw_text)
except json.JSONDecodeError:
    raise ConfigurationError("Malformed JSON configuration file.") # Root cause lost!
```

## Performance Considerations

1. **Exception Construction Overhead**: Constructing an exception object and capturing stack frames takes ~1 to 2 microseconds. In performance-critical inner loops executed 10,000,000 times per second, prefer returning sentinel values (`None` or `-1`) for normal expected outcomes rather than using `raise` for standard loop control.
2. **Traceback Generation**: Passing `from None` sets `__cause__ = None` and skips formatting the underlying exception traceback, slightly reducing memory and traceback formatting latency.

---

## Security Considerations

1. **Concealing Sensitive Data with `from None`**: Low-level database drivers often embed raw SQL queries containing passwords, credit card fragments, or internal server hostnames in their exception strings. When re-raising in public API controllers, use `from None` or sanitize the error message to prevent sensitive information leakage.
2. **Input Whitelisting**: Raise explicit `ValueError` exceptions immediately upon detecting unexpected input types to prevent injection attacks early.

- **FastAPI / Django REST Framework**: Raising `HTTPException(status_code=404, detail="Item missing")` inside endpoint controllers.
- **SQLAlchemy ORM**: Translating dialect-specific PostgreSQL/MySQL driver errors into unified `SQLAlchemyError` domain objects.
- **Cryptography Libraries**: Raising `InvalidSignature` when HMAC or RSA signature checks fail.

## Comparison: Raising Constructs

| Syntax | Traceback Origin | Attaches Cause? | Best Use Case |
|---|---|---|---|
| **`raise ValueError("msg")`** | Current line | N/A | Precondition / Validation errors |
| **`raise` (Bare)** | **Original line** | N/A | Re-raising after logging |
| **`raise NewErr from orig`** | Current line | **Yes (`__cause__`)** | **Exception Translation / Wrapping** |
| **`raise NewErr from None`** | Current line | **No (Suppressed)** | Hiding internal implementation traces |
| **`assert condition, "msg"`** | Current line | N/A | **Internal Debugging ONLY (Disabled by -O)**|

## Advanced Concepts: The `__traceback__` Attribute

In Python 3, every active exception object stores its complete call stack in the **`__traceback__`** attribute:

```python
import traceback

try:
    1 / 0
except ZeroDivisionError as err:
    tb_formatted = traceback.format_tb(err.__traceback__)
    print("Formatted Stack Trace:\n", "".join(tb_formatted))
```

You can even modify, attach, or customize tracebacks using the `with_traceback()` method before raising.

## Mini Project: Enterprise Payment Gateway Adapter & Exception Translator

### Requirements
Build a resilient payment gateway adapter named `payment_gateway_adapter.py` that translates low-level network and provider errors into structured domain exceptions, uses explicit chaining (`from err`) for diagnostic auditing, and uses `from None` for user-facing errors.

### Implementation Blueprint
```python
import random

# Domain Exception Hierarchy
class PaymentGatewayError(Exception): pass
class CardDeclinedError(PaymentGatewayError): pass
class NetworkProviderError(PaymentGatewayError): pass
class InvalidTransactionError(PaymentGatewayError): pass

# Mock Low-Level Driver Exceptions
class MockSocketTimeout(Exception): pass
class MockDriverCardExpired(Exception): pass

class PaymentGatewayAdapter:
    def __init__(self, merchant_id: str):
        self.merchant_id = merchant_id

    def process_charge(self, card_number: str, amount: float) -> dict:
        # 1. Precondition Validations
        if not isinstance(amount, (int, float)) or amount <= 0:
            raise InvalidTransactionError(f"Invalid transaction amount: ${amount}. Must be positive.")
        if len(card_number.replace("-", "").strip()) != 16:
            raise InvalidTransactionError("Invalid card format: Must be exactly 16 digits.")

        # 2. Simulate Low-Level Provider Driver Operations
        try:
            return self._dispatch_to_bank_network(card_number, amount)
        except MockDriverCardExpired as driver_err:
            # Explicit Chaining: Link domain error to technical cause
            raise CardDeclinedError("Card has expired or was rejected by issuing bank.") from driver_err
        except MockSocketTimeout as net_err:
            # Conceal internal banking IP from public consumer using from None
            raise NetworkProviderError("Banking gateway network timeout. Please retry in a few moments.") from None

    def _dispatch_to_bank_network(self, card: str, amt: float) -> dict:
        """Simulate low-level bank driver communication."""
        rand = random.random()
        if rand < 0.3:
            raise MockDriverCardExpired("BANK_ERR_54: Card Expired")
        elif rand < 0.6:
            raise MockSocketTimeout("TCP Timeout connecting to 10.240.12.88:8443")
            
        return {
            "status": "APPROVED",
            "tx_id": f"TX-{random.randint(100000, 999999)}",
            "amount": amt,
            "merchant": self.merchant_id
        }

if __name__ == "__main__":
    gateway = PaymentGatewayAdapter("MERCHANT_CORP_99")
    
    print("=" * 65)
    print("         PAYMENT GATEWAY EXCEPTION TRANSLATION TEST")
    print("=" * 65)
    
    test_scenarios = [
        ("4532-8901-2345-6789", -50.0),            # Invalid Amount
        ("1234", 100.0),                           # Invalid Card Length
        ("4532-8901-2345-6789", 250.00),           # Valid Card (Will simulate network/bank outcomes)
    ]
    
    for card, amt in test_scenarios:
        print(f"\nAttempting charge: ${amt} on Card {card[:4]}-****")
        try:
            res = gateway.process_charge(card, amt)
            print(f"  ✅ [SUCCESS] {res['status']}: TX ID = {res['tx_id']}")
        except InvalidTransactionError as inv_err:
            print(f"  ⚠️ [VALIDATION ERROR] {inv_err}")
        except CardDeclinedError as dec_err:
            print(f"  🚫 [CARD DECLINED] {dec_err} (Root Cause: {dec_err.__cause__})")
        except NetworkProviderError as net_err:
            print(f"  🌐 [NETWORK ERROR] {net_err} (Suppressed Cause: {net_err.__cause__})")
        except Exception as unhandled:
            print(f"  🚨 [UNHANDLED] {unhandled}")
            
    print("\n" + "=" * 65)
```

## Summary

In this lesson, you mastered Python's exception raising and chaining mechanics:
- Use **`raise ExceptionType("message")`** to actively enforce preconditions and domain constraints.
- Use a **bare `raise`** inside `except` blocks to re-raise active exceptions while preserving the original traceback.
- **Exception Chaining (`raise ... from exc`)** links high-level domain exceptions to their root technical causes (`__cause__`).
- Use **`raise ... from None`** to suppress internal implementation tracebacks, preventing sensitive information leaks.
- **Never use `assert`** for production input validation; `assert` statements are stripped in optimized mode (`python -O`).

- [ ] Use `from None` when exposing errors through public APIs to hide internal system paths.
- [ ] Use a bare `raise` when re-raising after logging.
